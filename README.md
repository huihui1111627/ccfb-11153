# 库存中台 Inventory Hub

服装品牌商同时在**天猫 / 京东 / 抖音 / 微信小程序**卖同一批货，四个平台各管各的库存，
大促一超卖就要挨个道歉。这个项目把四个渠道的库存与订单收进一个中台：
**一次分配、一处预占、一份流水**，并配一个运营后台。

TypeScript + Node（`node:sqlite` 持久化，零第三方运行时依赖），四个平台接口用 mock 起。
最后用一场模拟大促验收，**超卖件数**与**库存账实差**两个数都必须为 0。

---

## 快速开始

```bash
npm install          # 只有 typescript / @types/node 两个开发依赖
npm run build

npm test             # 43 个单元/集成用例（含两场端到端大促），约 30s
npm run sim          # 模拟大促压测 + 验收报告（默认 20s，见下方参数）
npm run demo         # 分步骤演示：分配 → 预占 → 支付 → 释放 → 盘点 → 同步 → 对账
npm start            # 常驻服务：中台 + 4 个 mock 平台 + 运营后台
```

`npm start` 之后打开 **http://127.0.0.1:8080/admin/** 就是运营后台。
默认数据落在 `data/hub.db`（演示环境，首次启动自动灌入初始数据）。

压测参数：

```bash
node --no-warnings dist/sim/flash-sale.js \
  --duration 30000        # 压测时长(ms)
  --stock 800             # 每个 SKU 初始库存
  --rps 120               # 目标下单速率
  --concurrency 8         # 驱动并发
  --chaos 3               # 故障倍率：限流/超时/5xx/重复/乱序按 3 倍注入
  --output report.json    # 落一份完整报告
```

常驻服务参数：`--port`、`--db`、`--stock`、`--pay-timeout`（默认 15 分钟）。

关键设计：**平台缓存永远滞后，只有中台能说“有没有货”。**
平台下单必须先同步调中台预占，预占成功才允许支付；库存数字通过异步推送（带版本号）
刷新平台本地缓存，只用来前置拦截明显没货的下单，不做最终裁决。

## 八条需求是怎么落地的

### 1. 总库存按比例或固定值分给渠道，剩余做共享池

`shops` 表里每个店铺有 `alloc_mode`（`ratio` / `fixed`）与 `alloc_value`。
分配基线是 **可分配量 = 实物 − 该 SKU 安全库存**：

- `ratio`：`floor(可分配量 × 比例)`
- `fixed`：固定件数

需求之和超过可分配量时按“**小渠道先削 → 低优先级先削**”回收，永不把渠道压到已预占以下。
**剩余量天然就是共享池**（`共享池 = 实物 − Σ渠道分配`），不需要单独一张表存正数余额。

### 2. 下单先预占，付款扣减，超时未付自动释放

- 预占：渠道分配优先，不够才借共享池；**任意一行不够就整单拒绝**，不会半预占。
  预占只动 `reserved`，不动物理库存。
- 支付：一个事务里 `onHand -= qty`、渠道 `allocated/reserved/sold` 同步变化、预占状态转 `PAID`。
- 释放：只回滚 `reserved`，物理库存不动。
- 超时：`releaseExpired(timeoutMs)` 批量释放；常驻进程每 5 秒扫一次。
- **晚到付款**：如果预占已被超时释放、平台随后才确认付款，`reviveAndPay()` 会按原订单行
  重新预占再扣减；确实没货才登记超卖并告警——不静默吞掉。

### 3. 平台接口限流/超时，同步失败要补偿而不重复扣

库存扣减只发生在预占/支付事务里；同步只负责“把当前可用数告诉平台”，
**重试推送不会再次扣任何库存**。

- 同步任务按 `(shopId, skuId)` 合并，新版本覆盖旧任务；平台侧以 `version` 幂等覆盖，旧版本直接忽略。
- 幂等键 = `shopId:skuId:version`，平台看到重复键返回 `duplicated`，看到旧版本返回 `staleVersion`。
- 失败按指数退避 + 抖动重试（429/超时/5xx 均可重试），超过上限进 `DEAD` 并发告警，
  `/admin/api/sync/repair` 按“本地最新版本 > 平台已确认版本”重新入队。
- 推送期间若同 SKU 来了更新版本，完成时不会把任务标成 DONE——新值继续排队（避免丢更新）。
- 平台健康、滞后 SKU 数、死信数都在后台可见。

### 4. 套装按子件库存算可售数

套装在 `bundle_components` 里展开为子件 × 用量：

- `套装可售 = min over 子件 floor(子件可售 / 用量)`
- 下单套装会按展开后的子件分别预占、扣减，流水记到子件上。
- 子件单独卖超后，套装可售立刻下降；子件不足时套装直接拒单。

### 5. 仓库盘点调整后差异按规则摊回各渠道

`applyStocktake` 支持三种规则：

| 规则 | 盘盈 | 盘亏 |
| --- | --- | --- |
| `pro_rata` | 按 `allocated` 权重分摊，尾差进共享池 | 按权重回收，尾差由共享池承担 |
| `shared_first` | 全部进共享池 | 共享池先吸收，不够再按权重 |
| `channel_first` | 渠道先按权重吃，剩余进共享池 | 渠道先承担，剩余进共享池 |

盘亏时如果**未付款预占已经超过实盘**，先把最晚下单的未付款订单释放（RELEASE），
再回收分配；绝不会让 `reserved > 实物` 或用“负数库存”掩盖。全程只改分配与实物，守恒不变。

### 6. 平台推送重复或乱序，处理结果不能变

事件按 `(channel, shopId, externalOrderNo, seq)` 唯一落库：

- **重复**：同 seq 再进来直接 `DUPLICATE`，无副作用。
- **乱序**：每次事件到来都把该订单**已收到的事件按 seq 重放**，推导目标终态，再只做“向前”修正。
  付款先到会用事件里的行自愈建单后直接扣减；取消先到会建单即释放。
- 同一事件集合（不论到达顺序）收敛到同一终态；`src/tests/events.test.ts` 用 10 种排列验证。
  “已释放后又收到支付”统一修正为 `CANCELLED`（净库存不变），避免终态依赖到达顺序。
- 同一 seq 出现两个不同事件类型 = `CONFLICT`，保留先到版本并告警。

### 7. 库存低于安全线时自动收紧小渠道分配

小渠道（`is_small`）只能吃“**实物 − 安全库存 − 主渠道分配**”之外的多余量；
库存越接近安全线，小渠道上限越小直至归零，让出的货回到共享池给主渠道用。
支付后立即检查一次，后台定时器每 3 秒全量扫一次；收紧是幂等的，不会反复削减。
每次收紧写 `REALLOCATE` 流水并产生 `SAFETY_TIGHTEN` 告警（同类告警去重，大促不刷屏）。

### 8. 每个 SKU 的库存变动都能追到订单或调整

所有变动只走 `ledger`，字段包含 `sku_id / channel / shop_id / reason / delta_on_hand /
delta_reserved / delta_allocated / delta_sold / ref_type / ref_id / note`。

- `ref_type` ∈ `ORDER | STOCKTAKE | ALLOCATION | SYSTEM`，`ref_id` 是订单号或盘点单号。
- 后台“链路追踪”按 SKU 展示完整流水；“预占流水”可按 SKU 或按单据反查。
- 对账直接校验 **流水汇总 `Σ delta_on_hand` == `stock.on_hand`**，任何一笔漏记都会被抓住。

## 验收：两个数都必须为 0

`npm run sim` 结束会打印：

```
✅ 守恒断言（分配/预占/共享池）
✅ 超卖件数 = 0
✅ 库存账实差 = 0（流水重放 = 账面）
✅ 分配守恒：Σ渠道分配 + 共享池 = 实物
✅ 渠道库存同步无滞后
✅ 重复推送被幂等丢弃
✅ 乱序消息最终一致
✅ 运行期无守恒违规
✅ 安全线收紧（跌线时才要求触发）
✅ 通过：超卖 0 件，账实差 0 处
```

- **超卖件数** = `oversold_events` 里真实无法履约的件数之和。正常路径下这个表恒为空；
  只有“付款成功但确实无货可扣”才会写入，并同步产生 CRITICAL 告警。
- **库存账实差** = ①每个 SKU 的流水汇总与账面 `on_hand` 的差 + ②`Σ渠道分配 + 共享池` 与实物的差。
  两处都必须为 0。
- 压测过程中每 ~250ms 采样一次守恒不变量，违规会被记录进报告——不只在收尾时检查。

参考运行（45s / 1500 库存 / 200 单秒 / 3× 故障）：

```
下单尝试 ~70000，平台受理 ~8400（大量请求被平台限流拒绝，用户侧重试后仍有
约 1/8 成功），最终 PAID ~5700、RELEASED ~2600
平台 HTTP 请求 ~126000（限流 ~68000 / 超时 ~2600 / 5xx ~4400）
Webhook 投递 ~22600（重复 ~4800 / 重试 ~2400），中台判定重复事件 ~690，冲突 0
平台缓存拦截 ~41000 次（缓存滞后但未占用中台库存）
→ 超卖 0 件，账实差 0 处
```

低库存场次（`--stock 120`）会因跌破安全线触发 `SAFETY_TIGHTEN`，同样零超卖零账实差。

## 运营后台

`npm start` 后访问 `/admin/`，5 秒自动刷新：

| 页签 | 内容 |
| --- | --- |
| 概览 | 实物/可售/订单状态/超卖件数/预警数/待同步，渠道同步健康卡片 |
| 渠道分配 | 每 SKU 实物、各渠道分配（含预占）、共享池、可售；一键重分配；盘点表单 |
| 商品与套装 | SKU 列表（含子件、安全线、低于安全线标记）；新建/编辑 SKU 与套装 |
| 店铺与规则 | 分配模式（比例/固定）、分配值、小渠道标记、优先级、平台地址 |
| 预占流水 | 全部流水表，正负用颜色区分，可追 `ORDER:` / `STOCKTAKE:` 来源 |
| 超卖预警 | 超卖 / 安全线 / 同步死信 / 拒单 / 盘点异常，可标记处理 |
| 同步补偿 | 各渠道待推送/重试/死信/滞后；立即补偿、对账修复；平台缓存 vs 中台快照 |
| 链路追踪 | 单 SKU 全量变动链路 + 当前分配快照 + 被哪些套装引用；一键系统对账 |

## 边界与取舍

- **SQLite 单文件 + 事务**：单机吞吐足够验证逻辑；真实多实例部署应把库存变更搬到
  MySQL/PostgreSQL 并给 `(shop_id, sku_id)` 加行锁或改用乐观锁版本。
- **预占同步调用**：平台下单必须等中台预占结果。真实对接若平台不支持同步预占，
  需改为“下单后立即异步预占 + 失败自动退款”的兜底链路；本文的幂等与释放机制可直接复用。
- **共享池没有独立余额表**：它被定义为 `实物 − Σ已分配`，任何分配动作自动改变共享池，
  天然守恒，少一处能对不上的账。
- **平台缓存**只用于前置拦截；它的滞后不会造成超卖，只在统计里体现为“缓存拦截”。
- 单进程内的定时器（同步、超时释放、安全线）都是演示用的；生产应拆成独立 worker 进程。
